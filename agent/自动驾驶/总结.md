### AgentsCoDriver [未中]

AgentsCoDriver 是一个面向网联自动驾驶（Connected and Autonomous Vehicles, CAVs）的多智能体协同驾驶框架。它的核心思想是把每辆车抽象成一个带有观察、记忆、推理、反思和通信能力的驾驶 agent：车辆先把当前道路、车道、自车状态、周围车辆状态等环境信息转成结构化描述，再结合历史经验、其他车辆消息和驾驶目标，由 LLM 进行高层决策，最后输出可执行的元动作，例如保持、加速、减速、变道、左转或右转。

- 论文：[[论文/AgentsCoDriver-Large-Language-Model-Empowered-Collaborative-Driving-with-Lifelong-Learning.pdf]]
- 图 1：The Scenario of Multi-Vehicle Negotiation

![[论文/图片/AgentsCoDriver-Figure1-Multi-Vehicle-Negotiation.png|700]]

图 1 展示的是 AgentsCoDriver 想解决的典型场景：多辆 CAV 在同一个交通空间内存在通行顺序、让行、变道或路口交互冲突，单车只靠自身观察容易做出局部最优决策，因此需要通过通信模块交换意图，再由各自的推理引擎结合消息进行协同决策。

- 图 2：Overall Architecture of AgentsCoDriver

![[论文/图片/AgentsCoDriver-Figure2-Architecture.png|800]]

这张图可以按“单车 agent 内部闭环 + 车车通信”来读：

- **环境到观察**：底部的 `Environments` 先把当前道路和周围车辆状态暴露给本车，本车通过 `Observation Module` 获取 observation，并编码成 LLM 能读的结构化场景描述。
- **观察到推理**：`Encoded Observation` 被送入 `Reasoning Engine`。推理引擎是核心决策器，会同时结合当前场景、驾驶目标、可选动作、历史经验和其他车辆消息，输出本车下一步高层动作。
- **记忆到推理**：`Cognitive Memory` 给推理引擎提供 `Related Memory`，也就是和当前场景相似的历史经验或常识。这里对应 few-shot experience，不是重新训练模型，而是在 prompt 里补充可参考案例。
- **动作到环境**：`Reasoning Engine` 输出 `Actions`，再作用到环境中，例如保持车道、加速、减速、变道、转向等。也就是说 AgentsCoDriver 的输出是高层离散驾驶动作，不是直接回归连续轨迹或底层控制量。
- **推理到通信**：`Communication Module` 根据本车状态、推理结果和通信需求生成消息，与右侧的 `Other Agents` 交换意图或协商信息。虚线箭头表示车辆之间传的是语言消息，而不是共享完整传感器数据。
- **反思到记忆**：执行后，`Reinforcement Reflection` 会接收观察、动作和推理过程，对本次决策进行评估和反思，再把有效经验写回 `Cognitive Memory`。因此系统形成“观察 -> 推理 -> 行动 -> 反思 -> 记忆 -> 下一轮推理”的持续学习闭环。

所以这张图的重点不是感知网络或控制器结构，而是说明每辆 CAV 都被封装成一个带有观察、记忆、反思、通信和 LLM 推理能力的 agent；多车协同主要发生在 `Communication Module` 和 `Reasoning Engine` 之间。

#### 要解决的问题

- 传统数据驱动自动驾驶系统通常解释性较弱，难以说明“为什么做出这个决策”。
- 单车智能受限于自身传感器范围，遇到遮挡、交叉口让行、汇入、超车等场景时缺少协商能力。
- 纯训练式模型的知识在训练完成后基本固定，面对新场景时持续学习和经验积累能力不足。

#### 核心模块

- **Observation Module**：提取当前交通场景的高层信息，例如车道数、自车位置/速度、周围车辆位置/速度等，并转成适合 LLM 使用的结构化文本。
- **Reasoning Engine**：把场景描述、目标、可选动作、历史经验和其他 agent 消息组合成 prompt，让 LLM 做逐步推理并生成最终驾驶决策。
- **Cognitive Memory Module**：维护常识记忆、经验记忆和反思记忆。系统会根据当前场景检索相似历史案例，作为 few-shot experience 辅助决策。
- **Reinforcement Reflection Module**：使用 evaluator 给决策质量打分，再由 reflector 生成文字化反馈，总结错误原因、正确做法和后续改进建议，并写入记忆。
- **Communication Module**：判断是否需要与其他车辆通信，并生成结构化消息，用于交换意图、补充观测和协商通行顺序。

#### 工作流程

1. 车辆 agent 观察当前环境，生成结构化场景描述。
2. 根据场景描述从记忆库中检索相似经验和反思记录。
3. 将环境、目标、可选动作、记忆和其他车辆消息输入推理引擎。
4. LLM 进行链式推理，输出高层驾驶动作。
5. 通信模块判断是否需要与其他车辆交换意图或协商。
6. 执行动作后，由 evaluator 和 reflector 评估本次决策，并把经验写回记忆库，实现持续学习。

#### 关键价值

AgentsCoDriver 的重点在于把“协同驾驶”从单车独立决策扩展到多车通信和协商。它利用 LLM 的语言推理能力表达驾驶意图、解释决策过程，并通过记忆与反思机制不断积累经验。因此它更像一个高层认知驾驶框架，而不是端到端感知-控制模型。

#### 局限

- 推理依赖 LLM，实时性不足，单次决策可能需要数秒，难以直接满足真实车辆的低延迟要求。
- 主要基于文本化场景描述，不直接处理原始视觉/激光雷达等多模态感知输入。
- 实验主要在 HighwayEnv 等仿真环境中验证，距离真实道路部署还需要解决感知、通信可靠性、安全验证和延迟控制问题。

### CoLMDriver

[协商] [协同决策] []

CoLMDriver，全称 **Cooperative Language-Model-based Driver**，是一个面向 V2V 协同自动驾驶的 LLM 驱动系统。它关注的问题比 AgentsCoDriver 更进一步：不仅让车辆用语言进行协商，还要把协商结果落到实时闭环驾驶控制中。论文把它定位为“从传感器数据到控制信号”的 full-pipeline LLM-based cooperative driving system，也就是从感知、协商、意图生成、轨迹规划到控制输出形成完整链路。

#### 要解决的问题

- 传统协同驾驶方法通常依赖固定通信协议、规则或优化目标，面对未见过的多车交互场景时泛化能力有限。
- LLM 虽然具备语言推理和协商能力，但直接用于自动驾驶会遇到两个核心困难：一是对连续道路空间和几何轨迹的规划能力不足，二是推理延迟不稳定，难以满足实时控制。
- 多车协同时并不是所有车辆都需要参与通信。如果所有车辆无差别协商，会引入大量冗余信息和延迟，因此需要判断“谁应该和谁协商”。

#### 核心思想

CoLMDriver 采用“高层语言协商 + 低层实时控制”的并行架构。高层管线以较低频率运行，负责用 LLM/VLM 生成驾驶意图、组织多车协商并达成通行共识；低层管线以较高频率运行，负责感知、waypoint 生成和控制执行。这样可以让 LLM 参与复杂交互决策，同时不阻塞车辆的实时规划控制。

#### 系统结构

- **LLM-based Negotiation Module**：负责多车语言协商。车辆会交换速度、位置、当前意图、历史对话等信息，并通过多轮对话达成谁先行、谁让行、谁变道等协作策略。
- **Dynamic Graph Grouping**：动态构建车辆交互图，只把未来可能发生冲突的车辆分到同一协商组中，减少不必要通信。它不是“全图所有车辆一直聊天”，而是谁的未来轨迹真有冲突风险，谁才进组协商。
  - **论文层面的当前图**：每辆车是一个节点，未来可能发生冲突的车对之间连边。这里的“可能冲突”不是简单看当前几何距离，而是根据各车未来 waypoints 导出的 safety score；如果两辆车的未来轨迹在时间和空间上存在较高冲突风险，就在它们之间加边。
  - **代码层面的冲突边**：公开实现中，每辆车先生成自己的预测轨迹，并存入 `planning_bank`。系统随后两两计算轨迹之间的最小距离，再把这个距离转换成 safety score；当 `safety score < 0.75` 时，这对车辆被视为有冲突，需要在图中连边。
  - **当前 negotiation group**：在当前车辆图上做 DFS，把连通分量收成若干 negotiation group。也就是说，只要一组车通过冲突边直接或间接相连，它们就进入同一个协商组。
  - **历史组与时间维稳定**：实现中维护 `nego_group_bank`，把和历史 group 有交集的新 group 合并起来，对应论文里的 `current groups + historical groups -> merge intersecting groups across temporal dimension`。同时用 `next_comm_time` 和 `nego_dur_bank` 控制刚谈过的组别不要立刻重开一轮协商，避免分组和协商在高频控制中抖动。
- **Negotiation Quality Evaluator**：作为 critic 对协商结果进行评估，关注三个维度：共识性、安全性、效率。评估结果会作为反馈进入下一轮协商，帮助车辆更快收敛到可执行策略。
- **VLM-based Intention Planner**：根据前视图像、检测目标、文本化状态等多模态信息，生成高层驾驶意图。意图主要包括导航意图和速度意图。
- **Intention-guided Waypoint Planner**：把高层语言/意图结果转换为可执行 waypoint。它使用 BEV 特征、目标点、导航意图和速度意图，通过 Transformer 结构生成未来轨迹点，再交给控制模块输出控制信号。

#### 协商流程公式

CoLMDriver 先把多车协同驾驶写成一个带消息交换的优化问题：

$$
\arg\max_{\theta,\mathcal{M}}\sum_{i=1}^{N} d\left(\Phi_{\theta}\left(\mathcal{X}_{i},\mathcal{D}_{i},\mathcal{M}_{i}^{k}\right)\right)
$$

其中，$\mathcal{X}_{i}$ 是第 $i$ 辆车的观测，$\mathcal{D}_{i}$ 是目的地，$\Phi_{\theta}$ 是驾驶框架，$d(\cdot)$ 是驾驶表现指标，$\mathcal{M}_{i}^{k}$ 表示第 $i$ 辆车经过 $k$ 轮语言协商得到的消息交换历史：

$$
\mathcal{M}_{i}^{k}=\left[\left\{\mathcal{M}_{i\leftrightarrow j}\right\}_{j=1}^{N}\right]^{k}
$$

动态分组部分的论文公式是：

$$
\mathcal{G}=\mathcal{H}^{T},\quad \mathcal{H}^{t}=\Phi\left(\mathcal{H}^{t-1}\cup\mathcal{C}^{t}\right)
$$

$$
\mathcal{C}^{t}=\bigcup_{k}\mathrm{DFS}\left(V^{t},\left\{\left(v_{i},v_{j}\right)\mid S_{s}\left(v_{i},v_{j}\right)\geq\theta\right\}\right)
$$

这里 $\mathcal{C}^{t}$ 是当前时刻根据冲突边做 DFS 得到的连通组，$\mathcal{H}^{t}$ 是融合历史后的 group bank，$\Phi(\cdot)$ 负责合并和历史组有交集的新组。注意论文公式里的阈值方向取决于 safety score 的定义；公开代码实现里是 `safety score < 0.75` 判定为冲突并连边。

在一个包含 $n$ 辆车的协商组中，第 $i$ 辆车在第 $K$ 轮的 LLM 输出可以写成：

$$
O_{\mathrm{LLM}_{i}}^{K}=
\mathrm{LLM}_{i}\left(
f_{P}\left(
\bigcup_{j=0}^{n}I_{j},
\bigcup_{k=0}^{K}\bigcup_{j=0}^{n}O_{\mathrm{LLM}_{j}}^{k},
S^{K-1}
\right)
\right)
$$

这个式子对应“本轮怎么说”：$I_{j}$ 是组内第 $j$ 辆车当前共享的信息，例如速度、位置、驾驶意图；$\bigcup O_{\mathrm{LLM}_{j}}^{k}$ 是历史对话；$S^{K-1}$ 是上一轮 evaluator/critic 给出的建议；$f_{P}$ 是 prompt 组织过程；输出 $O_{\mathrm{LLM}_{i}}^{K}$ 可以包含本车动作、对其他车的请求或回应。

每轮协商后，evaluator 会先把本轮对话汇总成各车意图，再用 waypoint planner 生成未来轨迹，并从三个角度打分：

$$
S_{c}^{k}=\mathrm{LLM}_{c}\left(\bigcup_{j=0}^{n}O_{\mathrm{LLM}_{j}}^{k}\right),\quad
\left[S_{s}^{k},S_{e}^{k}\right]=\mathcal{F}\left(\bigcup_{j=0}^{n}W_{j}\right)
$$

其中 $S_{c}^{k}$ 是共识分数，判断所有车是否愿意执行当前协商策略；$S_{s}^{k}$ 是安全分数，$S_{e}^{k}$ 是效率分数，二者由预测 waypoint $W_{j}$ 计算得到。最后 evaluator 用分类器/规则 $\Psi$ 生成反馈：

$$
\mathcal{R}=\Psi\left(S_{c}^{k},S_{s}^{k},S_{e}^{k}\right)
$$

$\mathcal{R}$ 会作为下一轮协商的 critic suggestion 输入 negotiator。整体上就是：**车辆先说一轮 -> evaluator 看共识/安全/效率 -> 给反馈 -> 下一轮车辆根据反馈改说法和改意图**，直到协商收敛或达到最大轮数。

#### 工作流程
1. 低层感知模块处理传感器输入，生成 3D 目标信息和 BEV 特征。
2. VLM-based intention planner 结合视觉、目标检测和文本状态，生成每辆车的初始驾驶意图。
3. 系统根据未来 waypoint 的潜在冲突关系构建动态车辆图，把相关车辆划入协商组。
4. 组内车辆用 LLM 进行多轮语言协商，表达自身意图、请求、让行或通过策略。
5. critic/evaluator 评估协商结果的共识、安全和效率，并把反馈提供给下一轮协商。
6. 达成共识后，最终驾驶意图被送入 intention-guided waypoint planner。
7. waypoint planner 生成几何可行轨迹，控制模块再输出车辆控制信号。
#### InterDrive Benchmark
论文提出了 **InterDrive**，一个基于 CARLA/V2Xverse 的多车交互驾驶基准，用来评估 V2V 协同能力。它包含 10 类典型高交互场景，主要覆盖三类任务：
- **Intersection Crossing**：多车从不同方向进入交叉口，需要协商通行顺序。
- **Lane Merging**：多车从不同方向汇入同一车道，需要处理合流冲突。
- **Lane Changing**：多车并排行驶并相互变道，轨迹之间存在交叉风险。
评价指标包括 Route Completion（路线完成度）、Infraction Score（违规/碰撞惩罚）、Driving Score（综合驾驶分数）和 Success Rate（完全成功率）。
#### 关键价值

CoLMDriver 的贡献在于把 LLM 的语言协商能力真正接入闭环驾驶系统。它不是只输出“加速/减速/变道”这样的离散高层动作，而是通过 intention-guided waypoint planner 将协商后的意图落到连续轨迹点上。因此它比纯文本式或离散动作式的 LLM driving agent 更接近可执行自动驾驶系统。

#### 和 AgentsCoDriver 的区别

- **AgentsCoDriver** 更强调多车 agent 的观察、记忆、反思和通信，核心是让车辆在仿真环境中通过 LLM 协商并持续学习。
- **CoLMDriver** 更强调完整闭环控制，把语言协商结果连接到 waypoint 生成和控制信号，目标是解决 LLM 协商与实时驾驶之间的落地问题。
- AgentsCoDriver 的输出更偏高层离散动作；CoLMDriver 进一步引入 VLM intention planner 和 waypoint planner，让协商结果变成可执行轨迹。
- CoLMDriver 通过动态分组和 critic-feedback 控制协商成本与协商质量，更关注实时性和多车冲突场景中的稳定收敛。

#### 局限

- 仍然主要在仿真环境中验证，真实道路中的通信丢包、延迟、异构车辆、不可信消息等问题还需要额外处理。
- LLM/VLM 推理仍然带来计算负担，即使采用并行架构，也需要车端或边缘端具备较强算力。
- 论文指出当前语言交互示例的多样性仍有限，未来需要构建更复杂、更丰富的交互场景来提升适应性。

### LangCoop: Collaborative Driving with Language

LangCoop 是一个面向多智能体协同自动驾驶的语言通信框架。它的核心观点是：在 V2V/V2X 协同驾驶中，车辆之间不一定要直接传输原始传感器数据、BEV 特征或检测结果，也可以把关键场景信息、目标、意图和决策理由压缩成自然语言消息进行交换。自然语言既足够紧凑，又能保留语义和推理信息，因此适合作为异构车辆之间的协同通信媒介。

#### 论文与框架图

- 论文：[[论文/LangCoop-Collaborative-Driving-with-Language.pdf]]
- 图 1：LangCoop framework overview

![[论文/图片/LangCoop-Figure1-Framework.png|800]]

#### 要解决的问题

- 原始图像、点云等传感器数据通信带宽开销很大，容易带来延迟、丢包和通信基础设施压力。
- 中间特征通信虽然压缩了数据量，但不同车辆可能使用不同传感器、网络结构或下游任务，特征空间不一定兼容。
- 只共享检测框、占用图、BEV 语义等下游结果时，可能丢失场景上下文、驾驶意图和决策理由。
- 传统通信形式更偏感知层协同，难以直接表达规划层或控制层协同，例如“我准备减速让你先过”。

#### 核心思想

LangCoop 将自然语言作为协同驾驶的信息载体。每辆车先用 LVLM 对前视图像进行结构化理解，提取场景描述、交互对象、导航目标和未来意图；再通过 LangPack 把这些信息打包成简洁文本消息；其他车辆接收后，将自身感知与外部 LangPack 聚合，进一步生成驾驶信号。
这种设计的重点不是“车辆之间聊天”，而是把语言当成一种低带宽、可解释、跨模型兼容的语义通信协议。

#### 核心模块

- **M3CoT（Mixture Model Modular Chain-of-thought）**：把驾驶场景理解拆成多个推理阶段，包括整体场景描述、交互对象描述、导航目标理解和未来意图描述。不同阶段可以使用不同 LVLM，从而在成本、推理能力和视觉理解能力之间做权衡。
  - 例如一辆 CAV 正接近无信号路口，前方有一辆车减速，右侧车道有车辆准备汇入。M3CoT 分阶段提问：
    1. **整体场景描述**：当前是城市路口，视野良好，前方路口有交互风险，车流中等。
    2. **交互对象描述**：前车正在减速，可能准备让行或转弯；右侧车辆靠近本车路径，存在汇入冲突；行人/骑行者若出现也需要标出。
    3. **导航目标理解**：本车目标是继续直行通过路口，而不是右转或停车。
    4. **未来意图描述**：本车应先减速观察，与前车和右侧车辆保持安全距离，必要时让右侧车辆先汇入，再平稳通过路口。
  - 这样做的好处是，视觉强的 LVLM 可以负责看图描述场景和对象，推理强的 LVLM 可以负责判断导航目标和未来意图，最后再把这些结果交给 LangPack 或驾驶信号生成模块。
- **LangPack（Natural Language Information Packaging）**：把车辆元数据、场景描述、对象描述、导航目标、未来意图等信息打包成标准化自然语言消息。单条消息通常小于 2KB，比图像通信节省大量带宽。
- **Driving Signal Generation**：把“本车理解 + 其他车 LangPack”转成下游能执行的驾驶信号。这里是把多车语义信息组织成 prompt，让 LVLM 输出结构化 JSON，再由后处理和控制器解析执行。
  - **输入**：本车前视图像、本车历史状态、本车目标点、M3CoT 生成的 scene/object/intent 描述，以及其他 CAV 发来的 LangPack。代码里本车历史会被整理成 JSON，例如时间戳、历史速度、历史曲率、相对 waypoint；其他车的信息会被整理成 `collab_agent_description`，包含其他车位置、意图描述，若共享图像则还会附带其他车前视图像。
  - **处理过程**：系统把 `scene_description`、`object_description`、`intent_description`、`target_description`、`ego_history_prompt`、`collab_agent_description` 拼进最终 `comb_prompt`，调用 LVLM 生成驾驶信号。然后用正则从模型回复中抽出 JSON，再解析成 tensor/dict。
  - **离散 waypoint 输出**：如果选择 `VLMPlannerWaypoint`，LVLM 直接输出 `predicted_waypoints: [[x_1,y_1], ...]`。后处理把它转成 waypoint tensor；控制器取最近的 waypoint 方向算 steering，并用 waypoint 距离估计 target speed。这种方式最直观，但论文实验发现零样本 LVLM 很难直接给出平滑、动力学可行的离散 waypoint，所以效果较差。
  - **连续轨迹参数输出**：论文默认采用这一类。LVLM 输出 `predicted_speeds_curvatures: [[speed_1, curvature_1], ...]`。后处理转成 `target_speed`、`curvature` 和固定 `dt=0.5`；控制器用 `target_speed` 做油门/刹车控制，用 `curvature` 近似换算 steering。若需要可视化或生成轨迹点，可以按速度和曲率随时间积分得到一条连续轨迹。因此它不是“直接回归 waypoint”，而是先生成速度-曲率序列，再由车辆运动学/控制器落到轨迹和控制。
  - **直接控制输出**：LVLM 也可以直接输出 steering、throttle、brake。优点是链路短，缺点是模型需要更稳定地给出低层控制量，跨场景泛化风险更高。

#### 工作流程

1. 每辆 CAV 使用车载前视 RGB 相机获取当前图像。
2. M3CoT 对图像和任务进行分阶段推理，生成场景、对象、导航目标和未来意图描述。
3. LangPack 将这些信息和车辆状态元数据压缩为自然语言包。
4. 车辆在通信范围内交换 LangPack，也可以和图像信息组合使用。
5. 接收方对其他车辆消息做坐标转换和时间对齐，再与自身感知结果融合。
6. LVLM 根据聚合后的多车语义信息生成结构化驾驶信号，例如 `predicted_speeds_curvatures`、`predicted_waypoints` 或直接控制量。
7. 后处理模块解析 JSON，并交给控制器转换成 steering、throttle、brake；默认连续轨迹形式是用 `target_speed + curvature + dt` 生成控制/轨迹。

#### 实验设置与结果

论文在 CARLA 闭环仿真中评估 LangCoop，使用 Town05 中 10 个测试场景，每个场景包含两个由 LangCoop 控制的 CAV，并与 CARLA traffic manager 控制的车辆、行人、自行车等动态参与者交互。通信范围设置为 200m。

主要评价指标包括：

- **Driving Score（DS）**：综合路线完成度和违规惩罚。
- **Route Completion（RC）**：路线完成比例。
- **Time Consumed（TC）**：完成路线或失败前消耗的时间。
- **Transmission Bandwidth（TB）**：车辆间平均传输数据量。

实验表明，LangPack-only 通信只需要约 1.8KB 的带宽，却能明显优于无协同和仅图像通信；相较图像通信，带宽减少超过 96%。如果同时传输 Image + LangPack，性能通常更高，但带宽也显著增加。因此 LangPack 的意义在于给出了一个“性能足够强、带宽非常低、语义可解释”的协同通信折中点。

#### 关键价值

LangCoop 的贡献在于把协同驾驶中的“通信媒介”本身作为核心问题来处理。它不像 CoLMDriver 那样重点构造语言协商到 waypoint 的完整闭环控制系统，也不像 AgentsCoDriver 那样强调记忆、反思和持续学习；它更关注如何把多车协同需要的信息压缩成自然语言，使不同模型、不同传感器配置、不同能力的车辆也能共享可理解的驾驶语义。

#### 和 CoLMDriver 的区别

- **CoLMDriver** 强调“语言协商如何落到实时控制”，核心是 LLM negotiation、critic-feedback 和 intention-guided waypoint planner。
- **LangCoop** 强调“协同信息如何高效表达和传输”，核心是 M3CoT 与 LangPack。
- CoLMDriver 更接近完整闭环驾驶系统；LangCoop 更像一种可插入多车协同系统的语言通信范式。
- CoLMDriver 关注冲突车辆之间的协商收敛；LangCoop 关注自然语言是否能替代图像、点云、特征、检测结果等高带宽通信媒介。

#### 局限

- 依赖 LVLM 的零样本理解和推理能力，模型选择、prompt 设计会显著影响驾驶表现。
- LVLM 推理仍有计算和延迟压力，真实部署中可能需要更小的蒸馏模型或快慢系统配合。
- 当前控制生成还没有充分融合车辆动力学约束，未来需要结合 bicycle model、轨迹优化或多项式规划等物理可行性约束。
- 实验主要集中在 V2V，未来可以扩展到更广义的 V2X，例如路侧单元、应急车辆提醒、信号灯状态、道路安全消息等。
