# Agent架构

agen演进流程大致可以分为三个阶段，早期的提示词工程，到上下文工程，再到现在的驾驭工程

## weights
社区早期大多关注weights，即注重于如何训练一个更好的模型
早期模型能力还不够“聪明”，无法很好地理解复杂的自然语言指令，所以需要通过微调来激活和定制它的能力

核心问题：
- 权重空间编码也将知识、过程和策略过于紧密地耦合在了一个实体上，更新知识需要重新训练
	- 成本高、周期长（需要高质量数据、GPU算力）以及训练之中遇到的种种问题
	- 知识时效性差，微调可能导致“灾难性遗忘”，即学习了新知识后，会“覆盖”掉模型原本已有的通用能力
	- 难以审计模型的行为
	- 个性化困难


**特点**：预训练，后训练，对齐，微调

### 记忆
####  记忆内容分类
- Working context，工作上下文
	- 当前任务的实时中间状态，比如打开的文件、临时变量、活跃假设、部分计划、执行检查点
- Episodic experience，情景经验
	- 它指过去某次执行中的结果的总结经验，比如决策点、工具调用、失败、结果、反思， 注重发生了什么
- Semantic knowledge，语义知识
	- 指跨越单次经历的抽象知识，比如领域事实、通用启发式、项目约定、稳定世界知识，注重什么成立
- Personalized memory，个人化记忆
	- 指关于特定用户、团队、环境的长期信息，比如偏好、习惯、反复出现的约束、历史互动。

记忆的本质在于将智能体在时间维度上的状态与其瞬时上下文解耦。相关的内容并非捆绑中的每一个外部元素，而是那些能够保持连续性的记录
#### 记忆结构

- **整体上下文** Monolithic Context 
- **检索存储上下文**  Context with Retrieval storage
	- 解决原始容量问题，引入记忆质量检索问题
		- GraphRAG 引入图和交流级检索
		- Engram 记忆压缩为潜在表示
		- SYNAPSE 统一情景-语义图（情景node，语义node，时间边，抽象边，关系边）
- **分层内存和编排**   Hierarchical Memory and Orchestration
	- 一旦平面检索证明不足以满足需求，系统便会转向分层记忆与编排。其核心思想是，并非每一条迹都应享有相同的保留策略
		- 提取  从长对话或工具结果里抽出真正值得记住的信息
		- 整合  把新信息和旧信息合并，更新冲突内容
		- 遗忘  删除过期、错误、重复、低价值的信息
	- 分类
		- 时空上的冷热分类
			- MemGPT
			- MemoryOS
		- 语义上的分类
			- MemoryBank  事件，用户资料，世界知识
			- MIRIX 
			- MemOS 显式记忆和隐记忆
			- Xmemory 主题-事件层次结构
- **自适应记忆系统** Adaptive Memory System
	- 上述架构仍然严重依赖人工设计的启发式方法。自适应记忆系统则更进一步，使模块、路由决策或检索策略能够响应经验变化
	- 核心转变：从 storage 到 control。早期问题是“怎么存更多记忆”，后续变成“怎么组织记忆”，自适应系统进一步关注“怎么控制记忆系统为当前任务服务”
	- 两类方向的区别：
		- **动态模块** Dynamic modules
			- 变的是记忆系统的结构或组件本身，比如编码方式、存储结构、检索器、管理模块可以被替换、调参、重组
			- 关注问题：记忆系统应该由哪些模块组成？模块之间怎么组织？模块本身能不能在运行中演化？
		- **基于反馈的策略最优化** Feedback-based strategy optimization
			- 结构基本不变，变的是控制策略，比如什么时候查、查哪里、查几条、怎么排序、怎么根据反馈调整权重
			- 关注问题：已有记忆模块基本固定时，当前任务应该怎么调用这些模块？

	- **MemEvolve**
		- 属于动态模块方向。它的关键不是只让 agent 积累经验，而是把 memory architecture 本身也作为可优化对象
		- 它把记忆生命周期抽象成模块化设计空间：
			- `encode`：原始经验被编码成什么形式，例如原文片段、摘要、embedding、事件三元组、图节点、工具调用轨迹
			- `store`：记忆存在哪里、按什么结构存，例如向量库、知识图谱、层次化记忆库、短期缓存、长期库
			- `retrieve`：怎么取记忆，例如 embedding 相似度、关键词 BM25、多跳搜索、图遍历、按时间或实体检索
			- `manage`：怎么更新、合并、遗忘、压缩、去冲突，例如合并重复记忆、删除过期记忆、把零散经验总结成规则
		- “独立演化”的含义：每个模块槽位都可以单独替换、调参、优化或重组，而不是重写整个 agent
			- 只改检索模块：从 Top-K 相似度变成“语义召回 + 图上多跳检索”
			- 只改存储模块：从单一向量库变成“短期缓存 + 长期知识图谱”
			- 只改编码模块：从保存完整对话变成“事件抽取 + 摘要”
			- 只改管理模块：从不遗忘变成“低价值记忆衰减 + 冲突记忆覆盖”
		- 代码类比：
		  ```text
		  旧架构：
		  Raw text -> Vector DB -> Top-K retrieval

		  动态模块演化后的架构：
		  Raw text -> Event extraction
		           -> Short-term cache + Knowledge graph
		           -> Multi-hop retrieval
		           -> Memory consolidation
		  ```

	- **MemVerse**
		- 也偏动态模块方向。它不是只在固定库里改排序，而是在短期缓存、长期图谱、抽象知识、轻量神经组件之间做结构化转换
		- 典型思路：短期记忆缓存保存近期经验，长期记忆用层次化知识图谱组织多模态经验，再周期性把关键知识蒸馏到轻量神经组件，实现更快的参数化召回

	- **MemRL / MoE gating / GAM**
		- 属于基于反馈的策略优化方向。它们通常不重点改变记忆系统的组件结构，而是学习更好的 memory usage policy
		- MemRL：不更新 LLM 权重，而是在 frozen LLM + external episodic memory 上学习检索策略。优化的是怎么用记忆，而不是模型参数
		- MoE gating：更像学习路由器，决定当前输入应该走哪些专家、哪些记忆通道或哪些检索组件
		- GAM：更像运行时的 just-in-time memory/context compilation。离线只保留基础记忆，运行时围绕当前任务多轮查找、反思、调整检索条件，再组装上下文
		- 代码类比：
		  ```text
		  输入 query
		  -> policy 判断：查向量库还是图谱？
		  -> policy 判断：取 3 条还是 10 条？
		  -> policy 根据历史反馈调整记忆权重
		  -> 返回当前任务上下文
		  ```
	- 简单记法：
		- 动态模块 = 学会改变记忆系统的“器官结构”
		- 反馈策略优化 = 学会改变记忆系统的“使用策略”




####  工具
- claude-code的延迟mcptool加载，暴露字段，后续用tool-search搜索工具
- 可以看作两个记忆层面：1 工具定义的跨对话和当前上下文解耦 2 工具调用后则保留在当前上下文中
	- 模型不自己去 MCP Server 里发现工具， Host 先连接 MCP Server，通过 `tools/list` 拿到工具元数据，然后把 MCP 工具包装成内部工具，例如：
	  ```text
	  mcp__github__create_issue
	  mcp__github__search_repo
	  mcp__draw__generate_image
	  ```
	- 这里不是一刀切。Claude Code 初始暴露给模型的工具大致分三类：
	  ```text
	  1. 内置工具或非 deferred 工具：
	     初始就完整暴露 name、description、input_schema。

	  2. deferred MCP 工具：
	     初始通常只暴露工具名索引，例如 mcp__github__create_issue，
	     不暴露完整 description 和 input_schema。

	  3. alwaysLoad 的 MCP 工具：
	     如果 MCP tool 的 _meta["anthropic/alwaysLoad"] 为 true，
	     即使是 MCP 工具，也会初始完整暴露。
	  ```
	- 如果 tool-search 没启用，或者模型/Provider 不支持这种 deferred loading，Claude Code 也可能退回到更传统的方式：把可用工具的完整 schema 直接放进本轮请求。也就是说，deferred loading 是一种按需暴露策略，不是 MCP 工具必然唯一的暴露方式。
	- 为了避免一次性把大量 MCP tool schema 都塞进上下文，Claude Code 在启用 tool-search 时会把多数 MCP 工具设为 deferred tool。模型第一轮通常只知道“有这些 deferred tool 名字”和“可以用 ToolSearchTool 查完整 schema”，但还不知道具体参数字段。
	- 例如用户说“帮我创建一个 GitHub issue”，模型一开始不能直接调用 `mcp__github__create_issue`，因为它还不知道参数是 `owner`、`repo`、`title`、`body`。它会先调用：
	  ```json
	  {
	    "name": "ToolSearchTool",
	    "input": {
	      "query": "github issue create"
	    }
	  }
	  ```
	- 真正执行搜索的是 Host 里的 `ToolSearchTool` 代码。它在 Host 保存的完整工具池中，按工具名、description、searchHint 等元数据匹配。只要 MCP Server 暴露的工具名和描述写得足够清楚，比如 `create_issue`、`Create a GitHub issue`，就能被 `github issue create` 这类 query 命中。
	- 命中后，Host 返回 `tool_reference`，表示这个 deferred tool 已经被发现：
	  ```json
	  {
	    "type": "tool_reference",
	    "tool_name": "mcp__github__create_issue"
	  }
	  ```
	- 下一次请求模型时，Host 会扫描历史消息中的 `tool_reference`，发现 `mcp__github__create_issue` 已经被展开过，于是把它的完整 schema 放进本轮 API 请求的 `tools` 字段：
	  ```json
	  {
	    "name": "mcp__github__create_issue",
	    "description": "Create a GitHub issue",
	    "input_schema": {
	      "type": "object",
	      "properties": {
	        "owner": {"type": "string"},
	        "repo": {"type": "string"},
	        "title": {"type": "string"},
	        "body": {"type": "string"}
	      },
	      "required": ["owner", "repo", "title"]
	    }
	  }
	  ```
	- 所以后续几轮通常不需要重新 ToolSearch。并不是模型永久记住了这个工具，而是 Host 每次构造请求时，根据历史里的 `tool_reference`，重新把已经发现过的工具 schema 暴露给模型。模型只有在当前请求的 `tools` 列表里看到这个工具，才能直接生成 tool_use。
	- 这体现的是一种 session 级别的工作集连续性：系统记住“这个会话里哪些 deferred tools 已经被发现并可继续使用”。但它不等同于长期 memory。工具 schema 本身更像 tool specification；真正接近 memory 的是“已发现工具集合”这种跨轮次状态，因为它让后续对话不用重复检索同一个工具。


###  技能
技能外化关注的是程序性专长，关注操作流程、决策启发式和规范约束。
在 harness 工程里，skill 不是“选中就能用”的独立文件，而是必须被记忆条件化、被协议绑定、被运行时治理约束，并通过执行反馈持续更新。
#### skill组成
- **操作流程**
	- 将复杂任务分解为步骤、阶段、依赖关系、停止条件
- **决策启发式**
	- 告诉模型分支处发生情况的处理办法
- **规范约束**：程序被视为可接受的条件
	- 一个工作流可能在技术上有效，但仍不合规、不安全或操作错误。 在实际部署中，执行受到测试要求、范围限制、访问权限、迹线期望以及特定领域操作规则的约束 
#### skill外化 流程
**规格**
- 典型形式包括 SKILL.md、指令文件、清单文件或其他声明式规范文档。
一个格式良好的技能规范应理想地涵盖五类信息，**即能力边界**、**适用范围**、前置条件、执行约束，以及示例和反例
**注册与发现**
能依赖于语义检索、结构化元数据、任务分解，或这些策略的组合
操作结构和语义
**渐进披露**
渐进披露就是 skill 的“按需展开”：先给模型看技能目录，确认相关后再给技能说明，真正执行时才给完整流程和材料。
**执行绑定**
把 skill 里写的“应该怎么做”，翻译成当前环境里真正能执行的工具调用、文件操作、API 调用或子智能体调用
- skill可能有工具说明，但具体还需要runtime绑定为具体环境工具
**组合**
常见的组合模式包括串行执行、并行分工、条件路由以及在更高级别技能中对子技能的递归调用

# 论文分析

## REACT: SYNERGIZING REASONING AND ACTING IN LANGUAGE MODELS

### 核心问题

现有的 LLM 求解复杂任务时,**推理(reasoning)** 和 **执行(acting)** 通常被割裂研究:
- 推理侧:思维链(CoT)等方法让模型生成中间推理步骤,但完全依赖内部参数知识,容易产生幻觉、误差累积
- 执行侧:动作生成方法让模型与外部环境交互,但缺乏显式的规划/状态跟踪机制,难以处理需要多步决策的复杂任务

**核心问题**:能不能让模型在生成过程中**交替进行推理和执行**,让两者互相增强而不是各自为战?

### 论文核心结论

存在。作者提出 **ReAct 范式**:让 LLM 以交错方式生成推理轨迹(reasoning traces)和任务特定动作(task-specific actions),实现推理与执行的协同。形式化地,对于给定任务,模型生成的输出序列为:

$$
\text{Thought}_1 \rightarrow \text{Action}_1 \rightarrow \text{Observation}_1 \rightarrow \text{Thought}_2 \rightarrow \text{Action}_2 \rightarrow \text{Observation}_2 \rightarrow \cdots
$$

其中:
- $\text{Thought}_t$:模型在第 $t$ 步的推理轨迹,用于任务分解、状态跟踪、策略更新、异常处理
- $\text{Action}_t$:模型在第 $t$ 步执行的具体动作(如调用 API、查询知识库、与环境交互)
- $\text{Observation}_t$:执行 $\text{Action}_t$ 后从外部源获得的反馈

- **推理轨迹**:
	- 提供一个"内部工作记忆",让模型能够显式地维护当前任务状态、下一步规划、以及从 Observation 中提取的关键信息，相当于让模型在执行前先"想清楚",而不是盲目地生成动作序列
	- Thought 可以**动态修正策略**:当 Observation 与预期不符时,模型可以在下一步 Thought 中识别问题并调整方案

- **外部交互**:
	- 纯推理方法(如 CoT)完全依赖模型内部参数中存储的知识,一旦推理链条中某一步出错,误差会向后累积
	- ReAct 通过 Action → Observation 让模型能够**从外部源获取实时信息**,用外部验证来校正内部推理
	- 这相当于给推理链装了一个"检查点"机制:每一步推理后,模型可以调用外部工具验证当前结论是否正确

- **协同效应**:
	- 推理帮助模型理解 Observation 的含义,并将其整合到当前任务规划中
	- 执行帮助模型获取推理所需的额外信息,避免纯靠"脑补"
	- 两者交替进行,形成"想→做→看结果→再想→再做"的闭环,这和人类解决复杂问题的方式非常相似

### 方法细节

#### 智能体与环境交互的正式设定

考虑一个智能体与环境交互以解决任务的一般设置。在时间步 $t$，智能体从环境中接收到观察 $o_t \in \mathcal{O}$，并根据某个策略 $\pi(a_t|c_t)$ 采取动作 $a_t \in \mathcal{A}$，其中

$$
c_t = (o_1, a_1, \cdots, o_{t-1}, a_{t-1}, o_t)
$$

是智能体的**上下文**，包含了从开始到当前时刻的完整交互历史。
当映射 $c_t \mapsto a_t$ 高度隐含且需要大量计算时，学习策略具有挑战性。例如，一个纯执行的智能体（Act-only）可能无法生成正确的最终动作来完成问答任务，因为它需要在多个信息源之间进行推理、整合、排除噪声，这些都隐含在从 $c_t$ 到 $a_t$ 的映射中。

#### 动作空间扩展到语言空间

ReAct 的核心扩展是将智能体的动作空间从传统的动作空间 $\mathcal{A}$ 扩展到

$$
\hat{\mathcal{A}} = \mathcal{A} \cup \mathcal{L}
$$

其中 $\mathcal{L}$ 是**语言空间**。这个扩展引入了两种截然不同的行为：

- **环境动作（$a_t \in \mathcal{A}$）**：会影响外部环境并产生观察反馈 $o_{t+1}$，如搜索、点击、移动等
- **推理迹/想法（$\hat{a}_t \in \mathcal{L}$）**：不会影响外部环境，因此不会产生观察反馈。它的作用是推理当前上下文 $c_t$，组合有用信息，并更新上下文 $c_{t+1} = (c_t, \hat{a}_t)$ 以支持未来的推理或行动

#### 推理迹的具体类型

论文明确指出，想法可以有各种有用的类型，包括但不限于：

- **任务分解与计划制定**：将复杂目标分解为子目标，创建行动计划
- **常识知识注入**：注入与任务解决相关的背景知识
- **信息提取**：从观察中提取关键部分，过滤噪声
- **进度跟踪与计划转换**：记录已完成步骤，判断何时切换策略
- **异常处理与计划调整**：当观察与预期不符时，识别问题并修正方案

这些推理迹本质上让模型能够在"不动手"的情况下"动脑"，通过内部推理来组织信息、规划路径，然后再采取行动。

#### ReAct 的具体实现

- **提示格式**：论文在 prompt 中提供少量示例（few-shot），每个示例展示一个完整的交错序列。对于语言推理任务，格式为：
  ```
  Question: [问题]
  Thought: [推理]
  Action: [动作]
  Observation: [观察]
  Thought: [推理]
  ...
  Final Answer: [答案]
  ```

- **解码机制**：模型按照示例格式自回归地生成交错序列。当生成到 Action 时，系统截断输出，解析动作指令，调用对应的外部工具/API，将返回结果作为 Observation 拼接到上下文，然后让模型继续生成下一步 Thought

- **不同任务的 Action 定义**：
	- **开放域问答（如 HotpotQA）**：Action 是搜索指令 `Search[query]`，Observation 是 Wikipedia API 返回的搜索结果段落
	- **事实验证（如 FEVER）**：类似搜索机制，通过检索获取证据文档
	- **交互式决策（如 ALFWorld、WebShop）**：Action 是环境允许的具体操作（如 `go to kitchen`、`take apple`、`click button`），Observation 是环境状态更新的文本描述

- **基线对比**：
	- **Act-only**：只有 Action → Observation，没有 Thought，相当于纯执行策略 $\pi(a_t|c_t)$
	- **Reason-only（CoT）**：只有 Thought，没有外部交互，完全依赖内部参数推理
	- **ReAct**：两者交替，利用推理迹更新上下文，再基于更新后的上下文采取动作

#### 为什么需要推理迹：一个具体例子

以多跳问答为例，假设问题是"A 电影的导演出生在哪座城市"。Act-only 智能体可能需要：
1. 搜索"A 电影 导演"→ 得到导演名字
2. 搜索"导演名字 出生地"→ 得到答案

但如果没有推理迹，模型很难：
- 判断第一步搜索结果是否包含足够的导演信息
- 从可能包含多个候选人的搜索结果中确定正确目标
- 在搜索结果有噪声或矛盾时决定下一步策略

而 ReAct 通过 Thought 可以显式地："我已经得到了导演名字是张三，接下来需要搜索他的出生地"，或者"搜索结果返回了多个人，需要进一步澄清"。这种显式的状态跟踪让模型能够处理更复杂的场景。



### 实验结论

- **语言推理任务**:
	- HotpotQA 和 FEVER 上,ReAct 显著优于 Reason-only 和 Act-only 基线
	- 具体来说,CoT 在这些需要外部知识的任务上容易"编造"答案,而 ReAct 通过搜索获取真实信息,大幅降低了幻觉
	- 同时,ReAct 生成的任务轨迹比 Act-only 更具可解释性,因为 Thought 提供了每一步的决策依据

- **交互式决策任务**:
	- ALFWorld:仅用 1-2 个 few-shot 示例,ReAct 的绝对成功率比模仿学习高 **34%**
	- WebShop:同样设置下,ReAct 比强化学习方法高 **10%**
	- 这说明 ReAct 的泛化能力很强,不需要大量训练数据,仅靠少量示例就能让模型理解任务结构

- **消融实验**:
	- 去掉 Thought(Act-only):模型容易执行无意义的动作序列,缺乏全局规划
	- 去掉 Action(Reason-only):模型在没有足够外部信息时容易幻觉
	- 两者结合效果最好,验证了推理和执行确实是互补而非冗余的

### 和 Agent 架构的关系

- ReAct 实际上给出了一个最小化的 LLM-based Agent 框架:
	- **Planning**:由 Thought 实现,模型在每一步推理中维护任务状态和下一步规划
	- **Tool Use**:由 Action 实现,模型调用外部 API 或环境接口
	- **Memory**:由 Thought + Observation 的累积实现,模型在推理轨迹中记录关键信息
	- **Action**:直接体现在 Action 的执行中

- 换句话说,ReAct 的 Thought-Action-Observation 循环,本质上就是 Agent 核心的 **"感知→思考→行动"** 循环的一个具体实现

### 限制与深层问题分析

#### 论文提到的限制
- 论文的实验主要基于 prompt-based 的 in-context learning,没有探索 fine-tuning 设置下的 ReAct
- 推理轨迹的质量高度依赖 few-shot 示例的设计,示例不好可能导致 Thought 质量下降
- 对于需要长期规划(数十步以上)的任务,仅靠局部的 Thought 可能不够,需要引入更显式的全局规划机制
- 外部交互的次数和效率也是一个问题:频繁调用 API 会增加延迟和成本

#### ReAct 范式的深层缺陷

**1. 贪心解码问题 (Greedy Decoding Problem)**
- **问题本质**: ReAct 采用自回归贪心解码,每一步只考虑当前最优的 Thought/Action,缺乏全局搜索策略
- **信息量不足**: 单步 Thought 提供的信息有限,无法进行深层次的全局规划,容易陷入局部最优解
- **后果**: 在多步任务中,某一步选择了看似合理的 Action,但可能导致后续步骤无法完成整体任务
- **举例**: 模型可能因为当前 Observation 的局部信息而做出短视决策,忽略了全局最优路径

**2. ReAct 的僵化性 (Rigidity / Inflexibility)**
- **固定交替模式**: Thought → Action → Observation 的严格循环结构过于死板
- **缺乏自适应能力**: 并非所有任务都需要严格的"想-做-看"循环
  - 有时需要连续思考多步(深度规划),如 ToT/GoT 的树状/图状推理
  - 有时需要连续执行多个动作(批量操作),中间不需要 Thought
  - 有时 Observation 显而易见,不需要额外 Thought 分析
- **无法动态调整粒度**: 模型不能根据任务复杂度自动调节推理和执行的频率

**3. 推理被打断的问题 (Interrupted Reasoning)**
- **核心矛盾**: 当模型正在进行深度推理时,强制插入 Action → Observation 会打断思维链的连贯性
- **后果**:
  - 复杂的逻辑推理需要连续性,频繁的外部交互破坏推理流
  - 模型可能"遗忘"之前的重要推理上下文(尤其在长序列中)
  - 增加了上下文窗口的负担,早期关键信息可能被稀释
- **适用场景受限**: 在数学证明、代码生成、逻辑推导等需要连续推理的任务中,ReAct 可能不如纯 CoT 有效

**4. 缺少显式状态机机制 (No State Machine)**
- **无明确状态管理**: ReAct 没有定义清晰的状态节点和状态转移规则
- **问题**:
  - 无法清晰表达"当前处于什么阶段"(如:探索阶段、执行阶段、验证阶段、回退阶段)
  - 无法根据不同状态切换不同的策略或 Prompt
  - 状态信息隐式地存在于 Thought 文本中,容易丢失、不一致或难以追踪
- **对比**: 有限状态机(FSM)、行为树(Behavior Tree)或图状态机可以更清晰地管理复杂任务流程,提供可预测的状态转换和异常处理

**5. 效率与成本问题**
- **频繁调用外部工具**: 每一步 Action 都可能涉及 API 调用,延迟和成本快速累积
- **冗余交互**: 某些 Thought 可能不需要外部验证,但固定格式强制要求执行 Action
- **上下文膨胀**: Thought + Action + Observation 的交替累积会快速消耗 token 预算,限制任务的步数上限

**6. Few-shot 示例的脆弱性**
- **高度依赖示例质量**: Thought 的格式、内容和推理风格严重受 few-shot 示例影响
- **泛化能力有限**: 遇到训练示例未覆盖的场景或新领域时,Thought 质量急剧下降
- **示例设计困难**: 需要精心挑选能展示完整推理-执行循环的示例,且不同任务需要不同的示例设计策略




### Agentless

#### 核心问题

Agentless 讨论的是软件工程 Agent 中一个很直接的问题: **解决 SWE-bench 这类仓库级 issue 修复任务,是否真的必须依赖复杂的自主 Agent 循环?**

典型 Agent 方案会把模型放进多轮闭环中:

$$
\text{观察仓库/问题} \rightarrow \text{决定下一步动作} \rightarrow \text{调用工具} \rightarrow \text{接收反馈} \rightarrow \text{继续规划}
$$

这类方案看起来更接近人类开发者,但会带来几个问题:

- **工具空间复杂**:模型需要学会何时搜索、何时打开文件、何时编辑、何时运行测试,还要遵守各种工具格式
- **决策链不可控**:一旦前面某步探索错了,后续规划会被错误上下文污染
- **轨迹难调试**:几十轮动作以后,很难判断失败到底来自定位、编辑、测试选择还是工具误用
- **成本高**:多轮交互会产生大量 token、环境调用和测试执行成本

Agentless 的反问是:如果把这些动作决策从模型手里拿回来,由系统写成固定工作流,模型只负责少数窄任务,效果会不会反而更稳定?

#### 核心结论

**不一定需要复杂自主 Agent。**

Agentless 的核心思想是把软件修复任务从"模型自主行动"改写为"系统级受控流程":系统固定阶段和数据流,LLM 只在每个阶段完成一个明确的小任务。它不让 LLM 自己决定未来动作,也不让 LLM 直接操作复杂工具,而是让 LLM 做:

- 从仓库结构中选可疑文件
- 从文件骨架中选相关类、函数、变量
- 从局部代码中选最终编辑位置
- 基于编辑位置生成 Search/Replace 形式的小补丁
- 在候选补丁和测试信号之间做辅助选择

换句话说,Agentless 不是"没有 LLM",而是 **没有开放式 Agent 控制权**。LLM 仍然参与推理和生成,但控制面在程序流程里,不是在模型的 Thought/Action 循环里。

#### 和 ReAct / SWE-agent 的根本区别

- **ReAct / SWE-agent**:模型在每一轮决定下一步 Action,例如搜索、打开文件、编辑、运行测试、根据反馈继续规划。模型既负责"想",也负责"决定做什么"。
- **Agentless**:系统预先规定阶段,模型只回答当前阶段的问题。模型不能自由决定"下一步我要运行什么命令",也不能在工具空间里自主探索。

因此,Agentless 更像一个 **LLM-powered workflow**,而不是传统意义上的 autonomous agent。它把 Agent 中最不稳定的部分,也就是开放式动作规划,替换成了固定的、可解释的工程管线。

#### 创新点 1: 分层定位/分层规划

Agentless 最重要的设计是 **coarse-to-fine 的分层定位**。严格说,它不是让模型生成一份长程 plan,而是把"如何找到应该修改哪里"这个问题拆成系统级层次:

1. **文件级定位**:先把整个仓库压缩成目录树/文件结构,让模型从宏观结构和 issue 描述中选出最可疑的文件
2. **元素级定位**:对可疑文件生成 skeleton,只保留类、函数、方法、变量声明等结构信息,让模型继续选相关代码元素
3. **编辑点定位**:再把相关元素的完整代码交给模型,要求它给出更细粒度的行号、函数或类级编辑位置

这个分层过程的价值在于:

- **降低上下文压力**:不把整个仓库塞给模型,而是一层层缩小搜索空间
- **保留结构信息**:目录树和 skeleton 比裸代码更适合模型判断"问题可能在哪个模块"
- **减少盲目探索**:模型不需要反复调用 grep/open/read 之类工具试错,定位路径由系统流程约束
- **便于调试**:如果最终补丁失败,可以分别检查文件级、函数级、行级定位是否偏了

所以它的"规划"创新不在于模型更会规划,而在于 **系统替模型做了任务分解**,把开放式规划变成了分层筛选。

#### 创新点 2: 暴露给模型的能力很少

Agentless 有意避免把完整开发环境暴露给 LLM。模型看到的不是一个可以任意操作的 shell 或编辑器,而是几个固定输入/输出接口:

- 输入仓库树,输出可疑文件列表
- 输入文件 skeleton,输出相关类/函数/变量
- 输入局部代码,输出编辑位置
- 输入 issue + 局部上下文,输出 Search/Replace 补丁
- 输入测试/候选补丁信息,辅助最终选择

这种设计相当于把工具使用从"模型自由调用"降级成"程序固定调用"。模型只需要完成语义判断和代码生成,不负责:

- 什么时候调用工具
- 调哪个工具
- 调用失败后如何恢复
- 是否继续探索
- 是否终止

这直接规避了很多 Agent 系统中的脆弱点:工具格式错误、动作空间过大、无意义探索、错误反馈被长期上下文放大等。

#### 创新点 3: LLM 定位 + embedding 召回的混合搜索

Agentless 复现实验中,文件级定位不是只靠 LLM 猜文件。官方流程会把 **LLM 选出的可疑文件** 和 **embedding-based retrieval 找到的文件** 合并。

大致做法是:

1. 先让 LLM 根据 issue 和仓库结构输出一批可疑文件
2. 再让 LLM 标出明显无关的目录,缩小后续检索范围
3. 对剩余文件建立向量索引,官方实现使用 OpenAI `text-embedding-3-small`
4. 用 issue 描述作为查询,通过向量相似度召回相关文件
5. 将 LLM 文件定位结果与 embedding 检索结果合并,得到最终文件候选

这个设计的意义是:LLM 擅长根据目录名、模块名和问题描述做高层判断,但可能漏掉名字不明显、语义相关但路径不直观的文件;embedding 检索则可以补充语义相似的候选文件。二者结合提高了文件级召回率。

需要注意的是,这里的向量搜索不是 Agent 的长期记忆,也不是让模型自己搜索仓库。它只是分层定位第一步里的 **辅助召回通道**。最终控制流仍然是固定 workflow。

#### 创新点 4: Search/Replace 小补丁而不是整文件生成

在 repair 阶段,Agentless 不要求模型重写整个文件,而是要求它生成 Search/Replace 形式的补丁:

- `SEARCH`:原代码中需要被替换的连续片段
- `REPLACE`:替换后的代码片段

这样做有两个好处:

- **减少幻觉和无关改动**:模型只改局部片段,不容易重写大量无关代码
- **易于程序化应用与验证**:系统可以直接匹配原片段并替换,再统一跑语法检查和测试

这其实把"代码编辑"也变成了一个窄接口:模型负责生成局部 diff,真正的 patch 应用和验证由程序完成。

#### 创新点 5: 多样本生成 + 测试过滤 + 投票/重排

Agentless 不迷信单次生成。它会针对同一个 issue 采样多个候选补丁,再用传统软件工程信号筛选:

- 过滤语法错误补丁
- 运行已有 regression tests,排除破坏原有行为的补丁
- 在较新流程中还会生成 reproduction tests,检查补丁是否能复现并修复原 issue
- 对剩余补丁做去重、归一化、投票或重排,选择最终提交

这个点和 Agent 的"自我反思"形成对比:Agentless 不主要依赖模型自己判断"我写得对不对",而是把正确性判断交给可执行测试和程序化排序。可靠性来自外部验证,不是来自模型的长文本反思。

#### 简版完整流程

1. 输入 GitHub issue 描述和目标仓库
2. 构造仓库目录树,让 LLM 做文件级定位
3. 用 embedding 检索补充可疑文件,并与 LLM 结果合并
4. 对可疑文件生成 skeleton,让 LLM 选相关类、函数、变量
5. 给出相关代码内容,让 LLM 定位最终编辑点
6. 基于编辑点上下文,让 LLM 生成多个 Search/Replace 补丁
7. 对补丁做语法检查、测试过滤、去重、投票/重排
8. 选择最终 patch 提交到 SWE-bench 评测

#### 深层意义

Agentless 的贡献不只是"又做了一个修 bug 工具",而是提出了一个对 Agent 架构很有挑战性的基线:

> 在当前 LLM 能力下,很多软件工程任务的瓶颈未必是"让模型更自主",而是"把任务切得更清楚、把接口收得更窄、把验证做得更硬"。

它说明复杂 Agent loop 不是天然优越的。对于仓库级修复任务,一个分层定位、窄接口生成、测试驱动选择的工作流,可以在可解释性、成本和稳定性上形成很强的竞争力。

#### 限制

- **不是通用自主开发者**:Agentless 擅长 issue 修复,但不等于能自主完成开放式产品开发、需求澄清或大规模重构
- **依赖定位质量**:如果文件级或元素级定位漏掉关键位置,后续 repair 很难补救
- **依赖测试信号**:测试不充分或 reproduction test 生成错误时,补丁选择仍然可能偏
- **探索能力弱**:相比 SWE-agent 这类可交互 Agent,Agentless 不擅长根据运行时反馈临时改变调查方向
