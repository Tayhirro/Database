# 推荐系统设计

## 一、总体结构

推荐链路复用 Feed 的"召回 → 排序 → 快照"三段式，全部策略都是**接口 + 注册表**的分接口形态，
新增一个策略只需实现接口并注册为 Spring Bean，不改任何调用方代码。

```text
GET /blog/feed?mode=for_you
  → BlogFeedService
     ├─ 召回：RecallOrchestrator.multiRecall(["for-you","interest","cf","hot"], ctx)
     │    每个名字从 RecallStrategyRegistry 取一个 RecallStrategy 实现，
     │    通道不存在自动跳过；候选用 LinkedHashSet 保序去重
     ├─ 曝光过滤：FeedExposureService（for_you 专属，可降级）
     ├─ 排序：RankingStrategyRegistry.getStrategy("weighted") → rank(candidates, ctx)
     └─ 多样性：同一作者在前 2 条窗口内最多 2 次打散
```

## 二、召回层：四个通道，从简单到复杂

| 通道 | 注册名 | 简单→复杂 | 名额 | SQL 数 | 依赖信号 |
|---|---|---|---|---|---|
| 热门 | `hot` | 最简单 | 60 | 1 | 全站 7 天点赞数 |
| 兴趣 | `interest` | 中等 | 40 | 1 | 用户点赞 → 店铺类型 TOP3 |
| 社交偏好 | `for-you` | 中等 | 80 | 3 | 点赞过的作者 + 发现补齐 |
| 协同过滤 | `cf` | 最复杂 | 20 | 2 | 最近 10 篇点赞种子的共同点赞 |

名额配置在 `hmdp.recommend.quota`（for-you/interest/cf/hot），四个名额之和等于候选池 200；
某通道没取满时名额不转移，候选池按实际条数工作。

### 2.1 hot（热门召回，冷启动兜底）

一条 SQL：最近 7 天（UTC 回溯）内 `ORDER BY liked DESC, id DESC` 取 60 条。
不使用翻页时间边界（全局热度与时间边界语义不匹配，跳过是刻意设计）。
新用户 interest/cf 全空时，推荐页退化为"社交偏好发现路 + 全站热门"，永远有内容。

### 2.2 interest（兴趣召回）

一条 SQL 两段结构：内层把用户点赞过的博客按归属店铺类型聚合取 TOP3
（`tb_blog_like join tb_blog join tb_shop`），外层取这些类型下用户没点过赞、
也不是自己写的最新博客。排序 `create_time DESC, id DESC`，
翻页边界与 follow 通道一致（时间更早，或时间相同 id 更小）。

### 2.3 for-you（社交偏好召回，原有多通道前版本保留）

两条路：熟悉路（点赞过的作者，名额 min(quota/2, 偏好作者数×10)）+ 发现路（其余名额），
按点赞数/时间/ID 倒序。多通道改造后它的名额从 200 收缩为 quota.for-you（默认 80），
作者交互列表写入 `ctx.extra["authorInteractions"]` 供排序复用，避免重复查库。

### 2.4 cf（协同过滤召回，item-based CF）

两步：先取用户最近 10 篇点赞为种子（`cf-recent-likes` 可配），
再一条 SQL 统计"也点赞过种子的用户"还点赞了什么：

```sql
SELECT l2.blog_id
FROM tb_blog_like l1
JOIN tb_blog_like l2 ON l2.user_id = l1.user_id AND l2.blog_id != l1.blog_id
WHERE l1.blog_id IN (种子)
  AND l2.blog_id NOT IN (用户已点赞)
GROUP BY l2.blog_id
ORDER BY COUNT(DISTINCT l1.user_id) DESC, l2.blog_id DESC
LIMIT 20
```

共同点赞人数越多排越前。索引依据：`uk_blog_user(blog_id,user_id)` 前缀扫种子、
`idx_user(user_id)` 扫共同点赞人，中小数据量下查询成本可控。

## 三、排序层：四个策略，从简单到复杂

| 策略 | 注册名 | 公式概要 | 使用场景 |
|---|---|---|---|
| time | `time` | 发布时间毫秒倒序 | following 模式 |
| simple | `simple` | 0.5 新鲜度 + 0.3 热度 + 0.2 作者亲和 | 基线/测试 |
| weighted | `weighted` | 1.0 赞 + 0.6 评 + 0.3 新鲜 − 0.5 陈旧 + 熟面孔加成 | for_you 默认 |
| interest | `interest` | 0.40 类型画像 + 0.30 质量 + 0.20 新鲜 + 0.10 作者亲和 | 个性化备选 |

所有策略统一全序约定：**分数降序，同分按博客 ID 降序**，保证快照可复现。

### 3.1 interest 排序的个性化信号

`RankingContext` 扩展了两个 for_you 专属字段（BlogFeedService 构建，策略不查库）：

- `typeAffinity`：店铺类型 → 用户亲和度（0~1，最高赞类型归一化为 1.0），
  来自一条聚合 SQL；没有点赞历史时空 Map，策略取中性值 0.5；
- `shopTypeByShopId`：候选博客店铺 → 类型，对候选 shopId 去重后一次 `selectBatchIds` 查回。

公式：`0.40×类型亲和 + 0.30×liked/(liked+10) + 0.20×1/(1+小时/12) + 0.10×作者亲和`。
这是可解释的启发式分，不冒充训练出来的点击概率；分数只在同一次快照内可比。

## 四、冷启动与降级

| 场景 | 行为 |
|---|---|
| 新用户（无点赞） | interest/cf 空列表让位，for-you 发现路 + hot 兜底 |
| Redis 曝光服务故障 | filterUnseen 返回原候选（fail-open），记录告警 |
| 召回某条 SQL 异常 | 通道抛错由上层按 Feed 既有降级路径处理，不影响其他通道已返回的候选 |
| 候选不足 200 | 按实际条数排序入快照，不凑数 |

## 五、扩展指引

1. **新增召回通道**：实现 `RecallStrategy`，`getStrategyName()` 起名，
   在 `RecommendProperties` 加名额、`application.yaml` 加配置、`BlogFeedService` 通道列表加名字。
2. **新增排序策略**：实现 `RankingStrategy<Blog>`，保持"分数降序 + ID 平手"全序约定，
   注册表自动生效；要作为默认策略改 `FeedMode` 的构造参数。
3. **换向量召回/ES**：cf 通道整体替换即可——合同只有 `recall(ctx) → List<Long>`，
   数据源可以是任意引擎，MySQL 仍是真相源。
