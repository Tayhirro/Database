> [!abstract]
> 我现在越来越倾向于把“读代码”看成一件结构化的事：
> - 先找系统在解决什么问题
> - 先找最小闭环，而不是先看所有文件
> - 先理解控制流和状态迁移，再理解函数细节
> - 先看 happy path，再看失败路径和恢复机制
> - 先看结果如何产生，再看日志、hook、配置这些观测层

我以前读大项目源码，经常一上来就卡在两个地方。

第一个地方是 `__init__`。  
第二个地方是目录。

看 `__init__` 的问题在于，它经常只是对象装配点。它告诉你“系统拿到了哪些部件”，但不告诉你“系统为什么这样运转”。  
看目录的问题在于，目录天然是静态切分，但程序本身是动态执行。你把一个动态系统按静态文件夹去理解，脑子里就很容易只剩下一堆名字。

后来我慢慢意识到，读代码最重要的不是“从哪里开始翻”，而是：

> **先找到这个系统最小的可运行闭环。**

也就是，给它一个输入，它如何一步一步处理，最后如何停下来，输出什么结果。

这个闭环一旦抓住，剩下的很多文件就都只是挂件：有的是提供输入，有的是执行动作，有的是做容错，有的是做记录，有的是做扩展。结构会开始自动变清楚。

## “闭环”
代码先找闭环
1. 入口输入对象
2. 最小执行单元
3. 主循环
4. 停止条件
5. 异常处理
6. 输出产物
### 1. 最小输入对象
一层是**接口输入对象**：外部第一次把什么东西交给系统， 另一层是**运行时工作对象**：系统内部把什么东西拿来调度、推进、重试和收尾。
有的系统接口输入就是 request，内部也按 request 跑完一次请求响应，有的系统外面接住的是 request，内部真正跑的却是 task、job、attempt 或 step ，有的训练系统外面看起来接收 batch，真正影响统计和更新的却可能是 sample、micro-batch 或 gradient accumulation step，有的 agent/机器人系统外面接收 instruction，真正参与决策的却是 environment state、history 和 instruction 共同组成的运行状态。

> **最小输入对象决定入口边界；运行时工作对象和状态承载对象，决定核心抽象边界。**

1. 接口输入对象：系统暴露给外界的最小调用单位，比如 request、prompt、event、batch。
2. 运行时工作对象：系统内部真正被调度、推进、重试的单位，比如 task、job、attempt、episode。
3. 状态承载对象：上下文、记忆、资源、权限、结果挂在哪个对象上，比如 session、agent、workflow instance、environment。
真正的是后两层，会被主闭环使用，构建流程抽象边界。
### 2. 最小执行单元
一个系统被执行所需要拆分为的最小执行单元
### 3. 状态
状态分为三类：
- 内存状态
- 外部环境状态
- 落盘状态
内存状态包括 history、context、cache、stats、flags。  
外部环境状态包括数据库、文件系统、repo working tree、容器状态。  
落盘状态包括日志、轨迹、结果文件、patch、checkpoint。
### 4. 系统的主循环
这是最需要尽早找到的东西，复杂系统都可以看作一个循环：
```text
取状态 -> 做决策 -> 执行动作 -> 接收反馈 -> 更新状态 -> 判断是否结束
```
### 5. 终止
是成功提交就停，还是达到步数上限就停，还是异常退出 ，还是外层 reviewer 选优后结束，还是超时后触发自动收尾。
### 6. 异常处理
1. 错误如何分类
2. 哪些错误可重试
3. 哪些错误会触发恢复
4. 哪些错误会直接终止

### 7. 最后产出
很多代码看半天都觉得悬空，本质上是你没有抓住它最后要形成什么产物。
只有把结果路径看清楚，前面的控制流才会真正闭合。


## 一个很实用的判断标准：先找“谁驱动谁”

我现在读代码时，会反复问一句话：

> **这里是谁在驱动谁。**

是 `RunSingle` 在驱动 `Agent`。  
还是 `Agent` 在驱动 `Env`。  
还是 `Model` 在驱动 `ToolHandler`。  
还是外层 `RetryAgent` 在驱动多次 attempt。

这个问题的好处在于，它能让你把“调用关系”和“控制权关系”分开。

调用不等于控制。  
被调用也不等于核心。

很多模块看起来被频繁调用，但其实只是工具层。  
很多函数看起来代码量不大，但它们手里握着控制权。

所以我现在看到一个类，不会先问“它有多少方法”，而会先问：

> **它有没有控制循环、状态推进和结束判定的权力。**

有，就属于核心。  
没有，就先放在外围理解。

## 以 SWE-agent 为例，这个方法为什么有效

SWE-agent 这类项目很容易把人看晕，因为它同时有：

- run 层
- agent 层
- model 层
- tool 层
- env 层
- reviewer 层
- hook 层

如果按文件夹扫，很快就会觉得每一层都很重要，于是每一层都抓不住重点。
