# Spring / Spring Boot 运行全链路（从启动到结束）

> 目标：给一个“从运行到结束”的整体框架；本页先把 **启动流程** 写清楚，运行/结束先留骨架，后续再填细节。

## 0. 阅读方式

- 把流程分成三段：**启动（Boot 编排 + Spring refresh 点火）/运行（请求与后台任务）/结束（shutdown hook + close）**。
- 如果你在读源码：先定位当前处于哪一段，再往下钻实现细节。

---

## 1. 全生命周期地图（总览）

```
启动：
  main()
    -> SpringApplication.run(...)
         -> new SpringApplication(...)
         -> application.run(...)
              -> prepareEnvironment(...)
              -> createApplicationContext()
              -> prepareContext(...)
              -> refreshContext(...)  -> context.refresh()
              -> afterRefresh(...)
              -> callRunners(...)
              -> listeners.running(...) / ApplicationReadyEvent

运行：
  WebServer 接管请求（servlet/reactive）
  Scheduler/Async/消息消费等后台任务运行

结束：
  JVM shutdown hook / 外部信号
    -> context.close()
         -> 销毁单例、发布关闭事件、释放资源
```

---

## 2. 启动流程（先写清楚这段）

### 2.1 入口：`main()` 调用 `SpringApplication.run()`

典型入口：

```java
public static void main(String[] args) {
    SpringApplication.run(App.class, args);
}
```

你可以把 `SpringApplication.run()` 理解成：**“把应用启动到一个可用的 `ApplicationContext`”**。

---

### 2.2 先构造 `SpringApplication`：加载启动期扩展点

在 `new SpringApplication(primarySources)` 的构造阶段（Boot 2.x）会做几件关键的“启动准备”：

1. 记录主配置源（`primarySources`）
2. 推断应用类型（`WebApplicationType`：servlet/reactive/none）
3. 通过 `SpringFactoriesLoader` 从 classpath 扫描并加载：
   - `ApplicationContextInitializer`
   - `ApplicationListener`

> 解释：你业务工程里通常没有 `spring.factories`，但依赖 jar（例如 `spring-boot-autoconfigure`）里有，启动时会扫描 classpath 上所有 jar 的 `META-INF/spring.factories` 并合并生效。

---

### 2.3 执行 `application.run(args)`：把“材料”准备齐

`run(args)` 里（高层）可以按阶段理解：

1. 创建并触发 `SpringApplicationRunListeners`（发布 starting 等事件）
2. `prepareEnvironment(...)`
   - 构建 `Environment`
   - 加载配置源（命令行参数、`application.properties/yml`、系统属性、环境变量…）
   - 激活 profile，完成属性解析
3. `createApplicationContext()`
   - 根据 `WebApplicationType` 创建不同的 `ConfigurableApplicationContext` 实现
4. `prepareContext(context, environment, ...)`
   - 把 `Environment` 装进 context
   - 执行所有 `ApplicationContextInitializer`（在 refresh 之前改造 context）
   - 注册/触发一部分启动事件

到这里为止，你可以认为：**Boot 负责把“容器点火前的所有材料与钩子”都准备好**。

补充：启动事件（便于你对照日志/断点定位阶段）。不同版本细节略有差异，但大体可按这些里程碑记：

- starting：应用即将启动（context 还没创建）
- environmentPrepared：环境已准备好（配置源已加载）
- contextPrepared / contextLoaded：context 已创建并完成准备（但尚未 refresh 点火）
- started：refresh 已完成（容器已点火）
- ready：应用对外可服务（web server 已启动，runner 已执行完）

---

### 2.4 `refreshContext(context)`：真正点火的是 Spring Framework

Boot 进入 `refreshContext(context)` 后，核心是：

- `context.refresh()`

继续把它看成“点火键”：只要 refresh 成功，一个完整可用的 Spring 容器世界就被建立出来了。

`AbstractApplicationContext.refresh()` 是典型的模板方法，按大块阶段可以记成：

1. 准备上下文状态（active 标志、校验环境等）
2. 获取/创建 `BeanFactory`，并加载 `BeanDefinition`
3. 执行 `BeanFactoryPostProcessor`（能“改 Bean 定义”）
4. 注册 `BeanPostProcessor`（能“拦截 Bean 创建”——AOP 代理等常在这里介入）
5. 初始化事件系统并注册监听器
6. 实例化非懒加载单例 Bean（容器真正“长出对象”）
7. 发布 `ContextRefreshedEvent`

补充：**自动配置（Auto-Configuration）** 的“选哪些配置类”这一步，通常就发生在 refresh 期间：

- `@SpringBootApplication` → `@EnableAutoConfiguration`
- `@Import(AutoConfigurationImportSelector)` 在解析配置类时生效
- `AutoConfigurationImportSelector` 会通过 `SpringFactoriesLoader` 读取依赖 jar 里的 `EnableAutoConfiguration` 列表（Boot 2.x：来自 `META-INF/spring.factories`）
- 再结合 `@Conditional...` 过滤，最终把满足条件的 auto-config 作为配置类导入容器

> 后续你要补“运行阶段”时，很多现象都能回到这里解释：为什么 AOP 能生效、为什么某些 Bean 在启动就会被创建、为什么某些扩展点必须在 refresh 前注册等。

---

### 2.5 refresh 之后：runner 与 ready

refresh 完成后（仍在启动期）常见还有两步：

1. `afterRefresh(context, args)`：给子类/框架留的后处理钩子
2. `callRunners(context, args)`：执行
   - `ApplicationRunner`
   - `CommandLineRunner`

最后 Boot 会发布“应用已就绪”的信号（不同版本/实现略有差异），你可以把它抽象成：

- **ready**：容器已完成刷新、WebServer 已启动（如果是 Web 应用）、应用可以对外提供服务
